# 계정별 MFA·복구 코드·Passkey 설계

작성일은 2026-10-25이다. 독립 설계 검토 후 사용자가 진행을 승인했다. 상세 구현 계획과 실행 방식을 확정한 뒤 제품 코드를 변경한다.

## 목표와 범위

사용자는 계정마다 TOTP MFA를 설정하고 QR 또는 수동 키로 인증 앱을 등록할 수 있어야 한다. 휴대폰을 잃었을 때 일회용 복구 코드를 사용하며, 등록한 Passkey로 비밀번호 없이 로그인할 수도 있어야 한다.

기존 Go·SQLite·Vite 8·React·Tailwind·shadcn/ui·Lucide 구성과 Docker/네이티브 설치를 유지한다. Redis, 외부 인증 서버, 이메일/SMS, SSO, 관리자 전체 MFA 강제 정책, 세션 관리 목록 UI는 추가하지 않는다. 기존 사용자와 플러그인 데이터는 보존한다. 변경은 로컬 프로젝트에만 적용하고 원격 푸시·NAS 업로드는 하지 않는다.

## 선택한 접근

- 선택된 방향은 기존 비밀번호 로그인을 유지하고 TOTP·복구 코드와 사용자 확인 필수 Passkey 로그인을 함께 제공하는 것이다. 사용자가 이전 제안에 동의하고 로컬 구현을 요청했다.
- Passkey를 비밀번호 다음의 두 번째 단계로만 쓰는 방법은 비밀번호 없는 사용 경험을 제공하지 못하므로 채택하지 않는다.
- 외부 IdP에 인증을 위임하는 방법은 단일 서버 설치에 추가 의존성을 만들므로 채택하지 않는다.
- 아래의 시간 제한·보관·복구 정책은 구현자가 제안한 기본값이다. 설계 승인 시 함께 확정한다.

## 현재 구조와 변경 경계

`internal/core/auth.go`는 Argon2id 비밀번호 확인 직후 세션을 발급한다. 이 발급 로직을 공통 경계로 만들고, 필요한 인증이 완료된 경우에만 호출한다. 세션 쿠키 속성, Origin/CSRF 검사, 마지막 관리자 보호와 API 권한 체계는 유지한다.

`internal/core/db.go`에 v3 마이그레이션을 추가한다. `frontend/src/api.ts`는 로그인 성공과 MFA 대기를 구분하고, `App.tsx`의 로그인과 설정 메뉴를 연결한다. 기존 비밀번호 변경 기능은 계정 보안 화면 안에 유지한다. API 명세, CLI 도움말, 관련 테스트와 설치 문서도 변경 범위다.

## 로그인 정책

1. TOTP 미설정 계정은 기존 비밀번호 로그인과 동일하다. 기존 계정에 MFA를 자동 활성화하지 않는다.
2. TOTP 설정 계정은 비밀번호 확인 후 TOTP 또는 복구 코드를 요구한다. 이 단계에서는 정상 세션을 발급하지 않는다.
3. Passkey 로그인은 등록된 자격증명의 서명, RP ID, Origin, challenge, 사용자 확인(UV)을 검증한 뒤 세션을 발급한다. UV는 서버에서 필수로 검증하며 TOTP를 추가로 중복 요구하지 않는다.
4. Passkey만 등록했다고 비밀번호 경로에 MFA가 강제되지는 않는다. 비밀번호 로그인 경로도 보호하려면 TOTP를 활성화하라는 안내를 제공한다.
5. 복구 코드는 비밀번호를 대체하지 않고 TOTP를 대체한다. 비밀번호와 모든 등록 수단을 잃은 경우는 서버 운영자의 로컬 복구 절차를 사용한다.
6. 계정 비활성화·삭제·비밀번호/권한 변경이 인증 도중 발생하면 발급을 거부한다. 새 보안 수단 변경도 이전 인증 대기 상태를 무효화한다.

## 계정 보안 UI

모든 역할의 사용자가 자기 계정에 대해 설정 > 계정 보안에 접근한다. 기존 컴포넌트와 스타일을 사용하고 다음 세 영역을 제공한다.

- 2단계 인증. 활성 상태, 등록 또는 재설정·비활성화 버튼, QR, 수동 입력 키와 복사 버튼, 6자리 코드, 확인·취소.
- 복구 코드. 남은 개수, 최초 발급/재발급 직후의 코드 목록, 복사·텍스트 다운로드, 재발급 시 이전 코드 무효화 안내. 저장했다는 확인 후 화면을 닫는다. 이미 발급한 원문을 다시 조회하는 기능은 없다.
- Passkey. 등록 버튼, 이름, 등록·마지막 사용 시간, 이름 변경과 삭제. 지원하지 않는 브라우저·접속 환경에서는 이유를 표시한다.

로그인 화면에는 비밀번호 로그인과 Passkey 로그인 버튼을 둔다. 비밀번호 확인 후 MFA가 필요하면 TOTP 입력과 복구 코드 사용 전환을 제공한다. 코드에는 명시적인 레이블, 적절한 자동완성, 숫자 입력 힌트와 오류 알림을 둔다. QR만을 유일한 등록 경로로 삼지 않는다.

첨부 이미지는 기능 참고다. 이미지의 시크릿 키·QR를 복사하거나 코드/문서/테스트에 저장하지 않는다. 활성화 전 상태는 등록 중으로 표시하고 실제 코드 확인 전 활성화됨으로 표시하지 않는다.

## TOTP와 QR

- 계정마다 암호학적 난수로 별도 시크릿을 생성한다. 일반 인증 앱과 호환되는 SHA-1, 6자리, 30초 주기를 사용하고 서버 시간 기준 앞뒤 한 주기만 허용한다.
- URI의 issuer는 ModuDock이며 계정 이름과 함께 앱에서 구분된다. QR는 서버에서 PNG로 생성하고 제3자 QR 서비스에 시크릿을 전송하지 않는다.
- 등록 대기는 사용자·현재 세션에 묶여 10분 후 만료된다. 취소 또는 새 등록 시작은 이전 대기 키를 폐기한다. QR와 수동 키는 등록 대기 중에만 표시한다.
- 확인 성공 시에만 활성화한다. 재설정은 새 키 확인 전까지 기존 키를 유지하고, 성공 시 원자적으로 교체한다. 기존 복구 코드도 새 10개로 교체한다.
- 마지막 사용 시간 단계를 저장해 동일 코드를 재사용할 수 없게 한다. 두 요청이 동시에 들어와도 하나만 성공해야 한다. 활성화에 사용한 코드도 소비 처리한다.
- 비활성화는 기존 수단으로 재인증한 뒤 TOTP와 복구 코드를 삭제한다. Passkey는 별도로 유지한다.

## 복구 코드

- 활성화 시 10개를 발급한다. 각 코드는 최소 128비트 난수이며 사람이 옮기기 쉬운 구분자를 포함한다. 허용된 구분자만 정규화한다.
- DB에는 사용자에 귀속된 해시만 저장한다. 원문은 발급 성공 응답으로 한 번만 반환하고 로그·URL·브라우저 저장소에 남기지 않는다.
- 로그인 또는 재인증 시 코드 소비와 후속 인증 상태 생성을 같은 트랜잭션에서 처리한다. 동시 소비는 한 번만 성공한다.
- 재발급은 최근 재인증이 필요하고 이전 코드를 전부 원자적으로 무효화한다. 화면에는 남은 개수만 재조회할 수 있다.

## Passkey와 접속 주소

- Go의 WebAuthn 표준 구현을 사용하고 암호 검증을 직접 작성하지 않는다. 후보는 `github.com/go-webauthn/webauthn`이다. TOTP·QR 후보는 `github.com/pquerna/otp`이며 구현 시 호환 버전·취약점·라이선스를 확인하고 고정한다.
- RP ID는 명시된 `--public-url`의 호스트명이다. Origin은 scheme·host·port까지 정확히 일치시킨다. Host/프록시 헤더를 보고 임의로 RP를 확장하거나 여러 도메인을 자동 허용하지 않는다.
- 운영은 유효한 인증서의 HTTPS 도메인을 사용한다. 개발은 명시된 `http://localhost:포트`를 허용한다. PublicURL 미설정, 일반 HTTP LAN IP, 지원하지 않는 주소는 Passkey만 비활성화하며 기존 로그인을 망가뜨리지 않는다.
- RP ID를 DB에 고정하고 기존 자격증명이 있는 상태에서 호스트가 달라지면 Passkey를 조용히 재해석하지 않는다. 비밀번호/TOTP 경로는 유지하고 재등록 또는 로컬 복구를 안내한다. 같은 RP ID의 포트 변경은 정확한 Origin 설정을 갱신한다.
- 등록은 인증된 세션과 최근 재인증을 요구한다. 사용자마다 임의의 안정적인 WebAuthn user handle을 사용하고 이름 변경과 분리한다.
- discoverable credential과 UV를 필수로 요청·검증하고 attestation은 none으로 한다. 로그인 시작에는 사용자 이름이 없어도 된다. 자격증명 소유자와 반환된 user handle을 완료 시 검증한다.
- 복수 기기를 등록할 수 있으며 사용자당 최대 10개로 제한한다. 공개키, credential ID, authenticator counter/backup 정보, 이름, 생성/사용 시간을 저장한다. 개인키·생체정보는 서버가 받지 않는다.
- 서명 카운터는 동기화 Passkey의 동작을 고려해 라이브러리 정책에 맞게 검증하고 갱신한다. 구체적인 이상 처리 정책은 사용하는 버전의 공식 동작을 확인해 구현 계획에 기록한다.

## 인증 대기 상태·재인증·권한 경계

- MFA 로그인과 WebAuthn challenge는 5분, 등록 대기는 10분으로 제한한다. 목적·사용자·세션·계정 보안 버전을 구분해 다른 경로에서 재사용할 수 없게 한다.
- 비로그인 대기는 짧은 수명의 HttpOnly·SameSite 쿠키로 브라우저에 묶는다. 정상 로그인 쿠키와 구분하며 대기 쿠키만으로 보호 API에 접근할 수 없다. HTTPS에서는 Secure를 사용한다.
- challenge 완료와 세션 발급은 단회성·원자적이다. 실패 횟수, 사용자 및 IP별 제한과 저장 개수 상한을 두고 만료 데이터를 정리한다. 기존 로그인 Origin 검사와 요청 크기 제한도 유지한다.
- TOTP 등록/재설정/해제, 복구 코드 재발급, Passkey 등록/삭제에는 최근 5분 내의 재인증을 요구한다. 재인증 증명은 세션과 작업 종류에 묶인 일회용 값이다.
- 기존 TOTP가 있으면 비밀번호+TOTP/복구 코드 또는 등록된 UV Passkey로 재인증한다. TOTP가 없고 등록 Passkey가 있으면 해당 Passkey 또는 현재 비밀번호로 재인증한다. 첫 수단 등록은 현재 비밀번호를 확인한다.
- 새 보안 API는 본인 브라우저 세션만 허용한다. Bearer 토큰으로 비밀·복구 코드를 조회하거나 보안 수단을 변경할 수 없다. 토큰을 브라우저 세션으로 교환하지 않는다.
- 보안 수단의 실질 변경과 복구 코드 재발급은 현재 세션을 포함한 모든 웹 세션·대기 상태를 폐기하고 다시 로그인하도록 안내한다. Passkey 이름 변경은 인증 수단을 바꾸지 않으므로 로그아웃시키지 않는다.
- 일반 보안 수단 변경으로 기존 자동화 API 토큰을 일괄 삭제하지 않는다. API 토큰은 별도 자격증명으로 계속 작동한다는 경고를 표시한다. 비밀번호/역할/활성 상태 변경의 기존 토큰 폐기 규칙과 비상 복구의 전체 폐기는 유지한다.
- 감사 기록에는 행위·사용자·시간·요청 ID와 안전한 결과만 넣는다. 비밀번호, 코드, TOTP 시크릿, QR 원문, 개인키는 기록하지 않는다.

## 저장·암호화·마이그레이션

SQLite v3에 사용자 보안 버전과 TOTP 설정, 복구 코드, Passkey 자격증명, 만료되는 인증 상태를 추가한다. 사용자 삭제 시 연결 데이터를 함께 제거한다. 기존 사용자·작업·플러그인·API 토큰은 보존한다.

TOTP 활성 키와 등록 대기 키는 표준 AES-256-GCM으로 암호화한다. nonce를 매번 새로 만들고 사용자 ID·용도를 AAD로 묶는다. 암호화 키는 DB가 아닌 데이터 디렉터리의 `auth.key`에 보관한다. 최초 필요한 시점에 안전하게 생성하며 Linux에서는 디렉터리 0700, 파일 0600을 적용한다. Windows 개발 환경은 OS ACL에 의존한다.

암호문이 있는데 키가 없거나 손상되면 새 키로 덮어쓰거나 MFA를 무시하지 않고 관련 인증을 실패 처리한다. 비상 복구 명령은 손상된 TOTP를 복호화하지 않고 명시적으로 폐기할 수 있어야 한다. 백업은 일관된 DB와 `auth.key`를 함께 보관한다. 같은 볼륨의 키는 DB만 유출되는 경우의 방어이며 서버/전체 볼륨 침해를 막는 경계는 아니다.

보안 변경 중 경합은 계정 보안 버전과 트랜잭션 안의 상태 재검사로 막는다. 만료·사용 완료 상태의 정리는 기존 credential janitor에 통합한다. 마이그레이션 전에는 백업을 안내하며 v3 DB를 구버전 바이너리로 직접 열 수 없음을 문서화한다. 자동 다운그레이드는 만들지 않는다.

## 비상 복구와 운영

서버 파일 접근 권한이 있는 운영자용 로컬 명령을 제공한다. 예시 형식은 `modudock admin reset-mfa --data-dir ... --username ...`이며 명시적인 확인을 요구한다. 기존 데이터 디렉터리 잠금을 지켜 서버를 멈춘 상태에서만 실행한다.

해당 계정의 TOTP·복구 코드·Passkey와 모든 세션·API 토큰·인증 대기를 폐기한다. 사용자·권한·기존 비밀번호는 보존하고 감사 로그를 남긴다. 비밀번호까지 분실한 경우에는 별도 비밀번호 재설정 없이 MFA 초기화만으로 로그인할 수 있다고 안내하지 않는다. 이 요청에서는 비밀번호 분실 복구 전체를 새로 구현하지 않는다.

운영 서버의 NTP 동기화, HTTPS 역방향 프록시와 정확한 PublicURL, 키/DB 백업을 설치 문서에 포함한다. 서버 측 MFA 기능을 위해 Redis나 컨테이너 추가, 외부 클라우드 계정은 필요하지 않다. Passkey 동기화 여부는 사용자가 선택한 기기/자격증명 제공자에 따른다.

## 검증과 완료 조건

- v2 DB를 v3로 올려 기존 사용자·플러그인 데이터를 보존하며 기존 로그인 회귀 테스트를 통과한다.
- QR에 들어간 URI와 수동 키가 동일하고 등록 확인 전 MFA가 활성화되지 않는다. 취소·만료·실패·재설정 중 기존 키 유지도 검증한다.
- TOTP 시간 경계·재사용·동시 소비, 복구 코드 재사용·재발급·동시 소비를 테스트한다.
- MFA 미완료 보호 API 접근, CSRF/Origin 오류, Bearer 토큰의 보안 API 접근, 다른 계정/세션 증명, 만료·재사용 challenge를 거부한다.
- Passkey의 올바른 서명은 성공하고 잘못된 RP ID/Origin/challenge/user handle, UV 누락, 삭제된 credential과 비활성 계정은 실패한다.
- 인증 도중 비밀번호·권한·활성 상태·보안 수단이 바뀌면 이전 상태로 세션을 발급하지 않는다. 키 손상·누락은 fail-closed로 확인한다.
- 프런트 테스트에서 로그인 상태 전환, QR/수동 키, 복구 코드 일회 표시, Passkey 취소·미지원, 민감 정보가 저장소에 남지 않는 것을 확인한다.
- Go 테스트·race·vet, 프런트 테스트·타입 검사·빌드, Docker와 네이티브 스모크를 실행한다. 브라우저 가상 인증기 또는 실기기 검증을 구별해 기록하고 미실행 항목은 숨기지 않는다.
- 구현 완료 시 정확한 명령·결과·남은 제약을 기록한다. 이 설계 문서 작성만으로 기능 완료나 보안 검증 통과를 주장하지 않는다.

## 구현자에게 남기는 선택

테이블/라우트의 구체적인 이름, 목적별 상태의 직렬화 형식, 테스트 파일 분리, 컴포넌트 분할, 라이브러리 호환 버전 선택은 위 경계 안에서 최소 구현으로 결정한다. 공개 API 계약과 의존성 변경은 구현 계획 및 결정 기록에 남긴다.
