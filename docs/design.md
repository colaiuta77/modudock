# ModuDock Go 플랫폼 설계

2026-10-23 사용자 승인 후 구현 기준으로 확정했다. 제품명은 ModuDock Go, 소스 경로는 `D:/Documents/ChatGPT/ModuDock-Go`, 독립 저장소의 모듈명은 `modudock`이다. 아래의 `app`은 설계 당시 명령 예시용 이름이며 실제 실행파일 이름은 `modudock`이다. Git 원격 저장소는 아직 연결하지 않았다.

## 1. 목적과 확정 범위

Docker 이미지 또는 다운로드한 실행파일로 설치하는 단일 서버용 자동화·플러그인 관리 플랫폼을 만든다. 기존 ModuDock의 사용성은 활용하되 Python 백엔드, 기존 DB, FF 호환 계층, 오늘의 세일·Firebase·Android 연동은 이식하지 않는다.

사용자가 정한 기술은 Go, React·TypeScript·Vite 8, Tailwind CSS·shadcn/ui, Lucide Icons다. SQLite를 초기 저장소로 사용한다. Linux 서버·NAS를 우선 지원하고 Windows·macOS는 개발 실행을 지원한다.

초기 제품 범위는 로그인·계정·권한, 반응형 관리 콘솔, 작업·스케줄·로그, 외부 REST API, GitHub 플러그인 설치·활성화·업데이트·롤백, 플러그인 메뉴·설정이다. 확인용 예제 플러그인 하나를 제공한다.

2FA·계정별 세션 관리 화면, 파일관리, 터미널은 기존 후속 범위를 유지한다. 기본 로그인에는 안전한 세션 만료·폐기와 CSRF 방어를 포함한다. 클러스터, 분산 큐, 플러그인 마켓, 임의 프론트 코드 실행, 기존 DB/API 호환은 초기 범위가 아니다.

## 2. 대안과 권장안

| 방식 | 장점 | 비용과 제약 | 판단 |
| --- | --- | --- | --- |
| UI를 내장한 Go 코어 하나, 내장 작업 큐·스케줄러, 플러그인 자식 프로세스 | Docker와 네이티브 배포가 같고 상시 외부 서비스가 없다. | 한 서버·한 코어 인스턴스 범위다. 플러그인 보안 격리는 별도 과제다. | 승인한 구현안이다. |
| Go API와 별도 runner 서비스를 처음부터 운영 | 자원·장애 경계 및 독립 확장에 유리하다. | 서비스 등록·인증·배포·장애 복구가 늘어나며 Docker 없는 설치도 복잡해진다. | 실제 분리 필요가 생길 때 재검토한다. |

Go `plugin`의 `.so` 동적 로딩은 사용하지 않는다. 공식 문서가 OS 지원, 동일 툴체인·의존성 요구와 충돌 가능성을 명시하며 독립 배포 목표에 맞지 않는다. HTTP 서버를 플러그인마다 외부 포트로 띄우는 방식도 초기에는 사용하지 않는다.

## 3. 코어 구조와 의존성

- HTTP는 Go 표준 `net/http`를 사용한다. JSON API와 빌드된 SPA를 같은 origin·포트에서 제공한다.
- 프론트 빌드 결과는 `go:embed`로 실행파일에 포함한다. 설치 사용자는 Node.js나 프론트 빌드를 준비하지 않는다.
- DB 접근은 `database/sql`과 CGO가 필요 없는 `modernc.org/sqlite`를 사용한다. 도메인별 SQL과 순서가 있는 마이그레이션을 둔다. PostgreSQL 구현이나 범용 저장소 프레임워크는 미리 만들지 않는다.
- 작업 실행기와 스케줄러는 같은 코어의 내부 모듈이다. Celery·Redis·Python과 별도 worker/scheduler 서비스는 신규 제품에 포함하지 않는다.
- 구조화 로그는 표준 `log/slog`를 사용한다. 시간대 데이터는 실행파일에 포함해 최소 이미지에서도 스케줄 시간대를 해석한다.
- Go·SQLite 드라이버·프론트 패키지는 구현 시 지원되는 안정 버전으로 고정하고 실제 빌드 및 취약점 검사로 검증한다. Vite는 8.x 범위를 유지한다.
- 프론트 개발·릴리스 빌드에는 Node.js 24와 npm 잠금 파일을 사용한다. Go 빌드 도구도 배포 사용자가 아닌 개발·CI 환경에만 필요하다.

코어 실행 명령은 `modudock serve --data-dir <directory> --listen <address>`로 단순화한다. 기본 포트는 7438이다. 기존 프로그램과 같은 서버에서 시험할 때는 다른 포트와 데이터 디렉터리를 사용한다.

## 4. SQLite와 영속 작업 큐

코어 데이터에는 사용자·세션·API 토큰·플러그인·릴리스·메뉴·설정·작업·스케줄·감사 이벤트를 저장한다. 플러그인 데이터는 `plugin-data/<id>/`에 따로 둔다.

- WAL, 연결별 busy timeout·foreign keys, 짧은 쓰기 트랜잭션을 사용한다. 단일 쓰기 경로와 제한된 읽기 연결을 사용한다.
- DB 파일은 서버의 로컬 디스크 또는 Docker 로컬 볼륨에 둔다. NAS 내부 로컬 볼륨은 가능하지만 다른 장치에서 SMB/NFS로 마운트한 경로는 지원하지 않는다.
- 데이터 디렉터리 단위 OS 파일 잠금으로 코어가 두 번 실행되지 않게 한다. 여러 호스트에서 DB를 공유하거나 여러 replica를 실행하지 않는다.
- SQLite의 WAL 관련 수정이 포함된 버전을 선택하고 빌드된 드라이버의 실제 SQLite 버전도 확인한다.

작업 상태는 `queued → running → succeeded / failed / cancelled / interrupted`로 정의한다.

1. API가 입력과 권한을 검사하고 작업 및 관련 변경을 한 트랜잭션으로 저장한다.
2. 커밋 후 내부 알림으로 실행기를 깨운다. 알림 채널은 최적화일 뿐 실제 큐는 SQLite다. 주기 조회로 알림 누락도 회복한다.
3. 실행기는 짧은 트랜잭션으로 실행 가능한 작업을 선점한 뒤 트랜잭션 밖에서 실행한다. 동시 실행 수와 큐 최대 크기를 제한한다.
4. 실행할 플러그인 release ID·입력·요청자를 작업 생성 시 고정한다. 업데이트 중에도 기존 작업의 실행파일이 바뀌지 않는다.
5. 상태·진행률·시도 결과를 저장한다. UI는 SSE와 상태 조회로 갱신한다. SSE 재연결은 마지막 이벤트 ID 또는 전체 상태 재조회로 복구한다.
6. 정상 종료 시 새 작업을 받지 않고 유예시간 후 자식 프로세스를 종료한다. 비정상 종료 후 남은 `running` 작업은 `interrupted`로 표시한다. 대기 작업은 재시작 후 처리한다.

외부 API 호출·파일 변경 같은 부수효과는 DB와 원자적으로 묶을 수 없다. 이미 처리했지만 결과 저장 전에 종료될 수 있으므로 정확히 한 번 실행을 보장하지 않는다. 자동 재시도는 명시적으로 멱등성을 선언한 작업에만 제한 횟수로 허용한다. 나머지는 관리자가 결과를 확인해 재실행한다. 외부 API의 작업 제출에는 요청자 범위의 idempotency key를 지원한다.

취소·timeout은 상태 값만 바꾸지 않고 실행 context 취소와 자식 프로세스 종료를 연결한다. Linux에서는 프로세스 그룹 단위 종료까지 검증한다. 취소도 이미 발생한 외부 부수효과를 되돌리지는 않는다.

## 5. 스케줄과 로그

- cron·시간대·활성 상태·입력·다음 실행 시각을 SQLite에 보관한다. 초기 cron은 분 단위 5필드로 정의한다.
- 스케줄 실행 생성과 다음 실행 시각 갱신은 같은 트랜잭션으로 처리한다. `(schedule_id, scheduled_at)` 중복을 차단한다.
- 서버 중지 중 놓친 실행은 기본적으로 누적 재생하지 않고 다음 시각부터 재개한다. 동일 스케줄의 이전 작업이 실행 중이면 다음 실행을 건너뛰고 이력을 남긴다.
- 시스템·작업 로그는 JSON Lines 파일과 stdout에 기록하고 용량·보관 수를 제한한다. 인증·권한·플러그인 설치 등 감사 이벤트는 SQLite에 저장한다.
- 로그 화면은 코어가 정한 로그 파일만 검색·조회한다. 임의 호스트 파일 경로나 Docker socket으로 로그를 읽지 않는다. 대량 로그 전문을 SQLite에 모두 넣지 않는다.
- 공통 필드는 timestamp, level, component, plugin_id, task_id, run_id, user_id, request_id다. 토큰·비밀번호·민감한 요청 본문은 로그에서 제외한다.

## 6. 인증과 외부 API

외부 API는 다른 앱·서버가 코어 기능을 호출할 수 있는 인증된 REST API로 정의한다. 공용 인터넷에 무인증으로 공개한다는 뜻은 아니다.

- `/api/v1`로 버전을 구분하고 OpenAPI 명세·일관된 오류 응답·페이지네이션을 제공한다. UI도 같은 API를 사용한다.
- 브라우저는 HttpOnly 세션 쿠키, SameSite 및 origin/CSRF 검증을 사용한다. 세션 상태와 만료·로그아웃 폐기는 SQLite에서 관리한다.
- 초기 계정은 `app admin create`로 대화형 생성한다. 기본 관리자 비밀번호를 이미지에 넣지 않는다. 비밀번호는 Argon2id 계열 검증된 구현으로 저장한다.
- 역할은 관리자·운영자·조회자로 구분한다. 관리자만 계정, 토큰 권한, 플러그인 설치·릴리스를 변경한다.
- 하나의 신뢰 운영팀이 공유하는 서버로 설계한다. 운영자는 모든 공유 작업의 실행·결과·작업 로그 조회·취소와 스케줄 변경을 할 수 있다. 조회자는 시스템 상태·플러그인 메뉴·작업 상태와 읽기 전용 리소스만 볼 수 있고 작업 원문 입력·결과·로그에는 접근하지 못한다. 시스템·감사 로그와 민감한 설정 변경은 관리자 전용이다. 계정별 데이터 분리가 필요한 멀티테넌트 모델은 초기 범위가 아니다.
- 외부 클라이언트에는 범위·만료·폐기가 있는 Bearer API 토큰을 발급한다. 원문은 생성 시 한 번만 표시하고 저장 시 해시한다. 토큰 권한은 계정 권한보다 넓어질 수 없다.
- 기본 API에는 시스템 상태, 플러그인·메뉴 조회, 작업 제출·조회·취소, 스케줄 CRUD, 로그 조회를 포함한다. 공개 무인증 엔드포인트는 민감한 정보를 내보내지 않는 liveness 정도로 제한한다.
- 인증 실패 제한, 요청 본문 크기 제한, timeout, reverse proxy의 신뢰 범위를 포함한다. 네이티브 기본 listen은 loopback이고 외부 공개는 주소·TLS reverse proxy를 명시한다.
- 외부 서비스 호출은 표준 HTTP 클라이언트와 플러그인으로 수행할 수 있다. 범용 웹훅 편집기나 특정 서비스 연동은 초기 범위가 아니다.

OpenAPI 명세와 실제 핸들러의 요청·응답을 계약 테스트로 검증한다. 브라우저 세션과 API 토큰을 별개 인증 방식으로 유지해 장기 토큰을 브라우저 저장소에 넣지 않는다.

## 7. 플러그인 계약

신규 규약의 플러그인은 코어에 직접 링크하지 않는 실행파일이다. 초기 공식 SDK·예제는 Go로 제공하며 다른 언어는 동일 프로토콜을 구현하고 실행 환경을 별도로 갖춘 경우에만 확장할 수 있다. Python·Node 런타임이나 자동 패키지 설치를 코어에 번들하지 않는다.

manifest는 schema_version, id, version, core_api compatibility, protocol_version, OS·CPU별 artifact와 SHA-256, task·resource 선언, JSON Schema 설정·입력, 메뉴, 권한·필요 런타임, health check를 갖는다. 초기 공식 실행파일 규격은 Linux amd64·arm64다.

GitHub 설치 흐름은 다음과 같다.

1. 관리자가 GitHub 저장소 URL과 태그 또는 commit을 지정한다.
2. HTTPS GitHub API로 ref를 commit SHA로 고정하고 해당 commit의 manifest를 읽는다. 초기에는 공개 GitHub 저장소만 지원한다.
3. OS·CPU에 맞는 GitHub Release 산출물을 다운로드하고 manifest의 digest·크기·압축 해제 경로를 검증한다. 실행 경로·심볼릭 링크의 디렉터리 이탈을 거부한다.
4. 임시 디렉터리에 배치하고 프로토콜 호환성·health check를 확인한다. 임의 설치 스크립트나 저장소 소스 빌드는 실행하지 않는다.
5. 불변 release 디렉터리를 만들고 DB의 활성 release 참조를 한 번에 전환한다. 설치 실패 시 기존 버전은 계속 사용한다.
6. 업데이트도 동일 절차를 따른다. 실행 중인 작업이 참조하는 release는 삭제하지 않는다. 비활성화하면 새 작업을 받지 않고 대기 작업은 명시적으로 취소한다. 실행 중 작업은 완료시키거나 관리자가 취소한다.

Git 명령어와 Go 컴파일러가 설치 서버에 필요하지 않도록 GitHub API와 사전 빌드 산출물을 사용한다. private GitHub, SSH Git, 다른 Git 호스팅은 필요가 생길 때 인증 설계를 추가한다. digest 검증은 변조 감지이며 배포자의 신뢰성이나 안전성을 증명하지 않는다.

실행은 stdin/stdout의 버전 있는 JSON 메시지 프로토콜로 한다. 코어가 요청을 보내고 플러그인이 진행률·결과를 반환한다. stderr는 플러그인 로그로 수집한다. 요청/메시지 크기·실행 시간·출력량을 제한하고 shell 문자열 대신 명시적 실행파일과 인자를 사용한다. 초기에는 요청마다 실행하고 종료하며 항상 켜지는 플러그인 daemon은 지원하지 않는다.

플러그인 API는 `/api/v1/plugins/{id}/resources/...` 아래에 명시적으로 선언한 resource와 method만 연결한다. 코어가 인증·권한·검증을 수행한 뒤 프로세스에 전달한다. 관리자 경로를 덮어쓰거나 임의 unauthenticated route를 등록할 수 없다.

플러그인 데이터는 release 디렉터리 밖에서 보존한다. 플러그인 코드 롤백은 데이터 스키마 롤백을 보장하지 않는다. manifest에 `data_schema_version`을 필수로 선언하고 설치 데이터의 버전을 코어에 기록한다. 초기에는 동일 데이터 버전을 선언한 release 간 전환만 허용하며 버전 불일치·미확인은 업데이트·롤백 모두 차단한다. UI 경고 확인으로 우회하지 않는다. 데이터 형식 변경은 서비스 중지·백업·별도 검증·복구 절차가 필요한 후속 작업이며 코어의 자동 마이그레이션 대상이 아니다. 같은 데이터 버전을 선언한 플러그인의 실제 호환성은 작성자 테스트로 검증한다.

### 신뢰 경계

첫 버전은 관리자가 신뢰하는 플러그인을 설치하는 모델이다. 자식 프로세스 분리는 Go 코어의 메모리·크래시와 생명주기를 분리하지만 같은 OS 사용자 권한의 파일·네트워크 접근까지 차단하지 않는다. manifest 권한은 코어 API 호출에 적용하고 OS sandbox 권한이라고 표현하지 않는다.

코어·플러그인을 비root로 실행하고 불필요한 환경 변수·인증 비밀을 자식에게 전달하지 않는다. Docker socket·호스트 루트는 마운트하지 않는다. 악성 플러그인을 안전하게 실행해야 하는 요구가 생기면 별도 UID·runner·namespace 또는 제한된 WASM 실행 환경으로 보안 경계를 새로 설계한다.

## 8. 프론트와 메뉴

- React·TypeScript·Vite 8·Tailwind CSS·shadcn/ui의 현재 기반과 파란색 밝은 관리 콘솔 방향을 활용한다.
- Heroicons 대신 `lucide-react`의 필요한 아이콘을 정적 named import한다. 모든 아이콘을 순회·번들하는 동적 registry는 만들지 않는다.
- 플러그인 아이콘 이름은 작은 허용 목록에서 선택하고 모르는 값은 기본 Puzzle 아이콘으로 표시한다. SVG·HTML·JS 원문을 manifest에서 실행하지 않는다.
- 메뉴는 개요, 작업 이력, 플러그인 영역, 설정으로 나눈다. 설정에는 계정, API 토큰, 플러그인, 스케줄, 메뉴 편집, 전체 로그가 있다.
- 데스크톱 접기 상태 저장, 모바일 Sheet, 키보드 접근성, 권한별 바로가기와 상태 카드를 유지한다. 상태는 실제 API 데이터만 표시한다.
- 플러그인은 schema 기반 설정 폼·작업 실행·테이블을 선언한다. 메뉴 이름·순서·표시 여부를 관리자가 편집할 수 있다. 임의 React 번들 로딩은 초기 범위가 아니다.
- LocalMartSaleWorkspace·세일 전용 타입·FCM 설정·Android 화면은 신규 프론트에 포함하지 않는다.
- Lucide 및 채택한 패키지의 라이선스 고지를 배포 바이너리와 웹 UI 고지에 포함한다.

## 9. Docker와 네이티브 배포

동일 릴리스 태그에서 Linux amd64·arm64 실행파일과 멀티 아키텍처 Docker 이미지를 만든다. 프론트 빌드는 한 번 생성해 각 코어 산출물에 포함한다. 버전·commit·artifact checksum을 릴리스에 기록한다.

| 환경 | 설치 방식 | 영속 데이터와 실행 |
| --- | --- | --- |
| Docker / Synology Container Manager | 실행파일을 담은 이미지 한 개와 Compose 예제 | `/data` 로컬 volume, 내부 포트 7438, 비root UID/GID와 volume 권한 안내, `init: true`, health check |
| 일반 Linux 네이티브 | 아키텍처별 압축 파일 다운로드·검증·해제 | 전용 서비스 계정, 명시적 data-dir, systemd unit 예제, graceful stop |
| Synology 네이티브 | 호환 CPU의 실행파일과 DSM 부팅 작업 예제 | 지정한 로컬 볼륨 디렉터리, DSM 환경별 실행·종료·로그 검증 필요 |
| Windows·macOS 개발 | 개발 도구로 빌드 또는 개발 산출물 실행 | 임시 개발 data-dir, OS별 예제 플러그인. 서비스 설치·자동 업데이트는 지원 범위 밖 |

Synology에 일반 Linux의 systemd가 있다고 가정하지 않는다. Docker 설치를 먼저 검증하고 네이티브는 실제 DSM·CPU·실행 권한을 확인한 뒤 지원 상태를 표시한다. NAS 전체 모델 호환이나 SPK 패키지는 약속하지 않는다.

런타임 이미지에는 필요한 CA 인증서와 비root 사용자 환경을 포함한다. 플러그인이 실행되므로 처음부터 shell·라이브러리가 전혀 없는 이미지라는 가정은 하지 않는다. 코어와 공식 예제 플러그인은 CGO 없는 빌드로 맞춘다.

데이터 디렉터리는 `core.db`, `plugins/<id>/releases/`, `plugin-data/<id>/`, `logs/`로 나눈다. 코어의 DB·플러그인·로그 경로는 이 루트에서 계산한다.

업데이트는 운영자가 명시적으로 수행한다. 서비스 중지 후 DB와 plugin-data를 함께 백업하고 실행파일 또는 이미지 버전을 교체한다. 새 버전은 시작 시 마이그레이션 후 서비스를 연다. 스키마 비호환 롤백에는 백업 복원이 필요하다. SQLite WAL 사용 중 DB 파일 하나만 복사한 것을 정상 백업으로 취급하지 않는다.

## 10. 구현 순서와 합격 조건

1. Go 코어·SQLite 마이그레이션·프론트 내장·health check를 만들고 Docker와 Linux 실행파일 모두 같은 UI/API를 제공하는지 확인한다.
2. 계정·RBAC·세션·API 토큰·OpenAPI를 만들고 권한 거부, 토큰 만료·폐기, CSRF, 잘못된 입력을 테스트한다.
3. 영속 작업 큐·스케줄·로그를 만들고 재시작 후 queued 복구, interrupted 표시, 중복 제출·스케줄 방지, timeout·취소를 테스트한다.
4. 새 플러그인 manifest·예제·설치·활성화·업데이트·롤백·메뉴를 만들고 잘못된 digest, 경로 이탈, crash, 데이터 보존, 실행 중 업데이트를 테스트한다.
5. Lucide 관리 콘솔과 배포 문서를 완성하고 데스크톱·모바일·키보드 동작, 빌드·취약점 검사, Linux amd64/arm64 Docker 기동을 검증한다.

단계별 기능 테스트 외에 `go test ./...`, 지원 환경의 race test, `go vet ./...`, 프론트 테스트·프로덕션 빌드, Compose 기동과 재시작 검증을 수행한다. ARM64 에뮬레이션과 실제 NAS 검증은 구분해 보고한다.

## 11. 확정 사항과 후속 확인

- 권장 배포·플러그인 구조, 신규 프로젝트 이름·소스 경로가 승인됐다. Git 원격 연결과 공개 배포는 아직 수행하지 않는다. 기존 프로젝트와 운영 데이터를 덮어쓰지 않는다.
- 외부 API는 코어와 선언된 플러그인 리소스를 인증해 호출한다. 특정 외부 서비스 연동은 별도 요구가 필요하다.
- 실제 NAS 네이티브 호환성은 구현 후 대상 DSM·CPU에서 검증해야 한다.
- 구현자는 지원 버전에 맞는 cron·JSON Schema·migration·파일 잠금 패키지, 테스트 도구와 제한값을 선택하고 근거를 기록한다. 프레임워크·분산 시스템·새 기능을 추가할 재량을 의미하지 않는다.
