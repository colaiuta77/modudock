# MFA·Passkey 설정과 비상 복구

설정 → 계정 보안에서 본인의 로그인 수단을 관리합니다. 기존 계정은 자동으로 MFA가 켜지지 않습니다.

## TOTP와 복구 코드

1. `2FA 설정`에서 현재 비밀번호로 재인증합니다. 이미 2FA를 사용 중이면 인증 앱 또는 복구 코드도 필요합니다. 등록한 Passkey로 대신 재인증할 수도 있습니다.
2. 인증 앱으로 QR을 스캔하거나 시크릿 키를 직접 입력합니다. QR은 ModuDock 내부에서 생성하며 외부 서비스로 전송하지 않습니다.
3. 6자리 코드를 입력하고 `인증 및 활성화`를 누릅니다. 확인 전에는 활성화되지 않으며 재설정 중에도 기존 키가 유지됩니다.
4. 현재 브라우저는 새 세션으로 로그인을 유지하고 다른 기기의 기존 웹 세션은 종료됩니다. 같은 설정 화면의 복구 코드 카드에 코드 10개가 한 번 표시됩니다. 복사·TXT 다운로드로 보관한 뒤 저장 확인 후 닫기를 누르세요. 화면 이탈·새로고침·로그아웃 후에는 원문을 다시 조회할 수 없습니다.

복구 코드는 각각 한 번만 쓸 수 있으며 비밀번호와 함께 사용합니다. 재발급하면 기존 코드 전체가 즉시 무효화됩니다. TOTP를 해제하면 복구 코드도 삭제되지만 Passkey는 남습니다. 같은 TOTP 코드의 재사용은 거부되므로 등록 직후 다시 로그인할 때는 다음 코드 또는 복구 코드를 사용하세요.

TOTP는 SHA-1·6자리·30초 주기이고 앞뒤 한 주기를 허용합니다. NAS와 휴대전화의 시간 자동 동기화/NTP를 켜세요. QR 등록 대기는 10분, 재인증은 5분입니다. 먼저 재인증이 만료되면 같은 QR을 유지한 채 다시 인증할 수 있습니다.

## Passkey

- 운영에서는 고정 HTTPS 도메인을 `--public-url`에 설정합니다. 예를 들면 `https://modudock.example.com`입니다. Docker Compose는 `MODUDOCK_PUBLIC_URL`로 전달합니다.
- 개발은 명시적인 `http://localhost:포트`를 사용할 수 있습니다. 빈 public-url, 일반 HTTP LAN 주소, IP 주소는 Passkey를 지원하지 않습니다. 이 경우 비밀번호/TOTP는 계속 사용할 수 있습니다.
- 최신 브라우저의 WebAuthn JSON 변환 API가 필요합니다. 미지원 브라우저에는 안내가 표시됩니다. 브라우저/운영체제의 지문·얼굴 인식·PIN 등 사용자 확인을 요구합니다.
- 계정당 최대 10개를 등록할 수 있습니다. 등록·삭제 시 현재 브라우저는 새 세션으로 로그인을 유지하고 설정 화면의 목록을 갱신합니다. 다른 기기의 기존 웹 세션은 종료됩니다. 이름 변경은 세션을 교체하지 않습니다.
- Passkey는 비밀번호 없는 대체 로그인입니다. Passkey 로그인에 TOTP를 한 번 더 요구하지 않습니다. 비밀번호 로그인도 남으므로 비밀번호 경로까지 보호하려면 TOTP를 켜세요.
- RP ID는 도메인에 고정됩니다. 도메인을 옮길 때는 기존 주소에서 모든 계정의 Passkey를 먼저 삭제한 뒤 새 주소에서 재등록하세요. 기존 Passkey가 남아 있으면 변경된 호스트에서는 Passkey만 비활성화됩니다.

인증기의 개인키는 서버에 저장하지 않습니다. 서버에는 credential ID·공개키·사용자 연결·검증 메타데이터만 저장합니다. 백업 가능한 동기화 키의 카운터 경고는 감사 로그에 기록하고, 비동기화 키의 복제 경고는 로그인을 거부합니다.

익명 Passkey 로그인 시작은 IP당 15분에 8회로 제한합니다. 보안 자격증명 변경 시 아직 계정이 식별되지 않은 Passkey 로그인 대기는 함께 무효화하므로, 다른 사용자가 동시에 로그인 중이었다면 인증을 다시 시작해야 할 수 있습니다. 이미 로그인한 다른 계정의 세션은 종료하지 않습니다.

보안 화면을 떠나거나 계정을 전환하면 진행 중인 브라우저 요청과 인증기 작업을 취소합니다. 서버에 이미 반영된 변경까지 되돌리지는 않으므로, 전송 직후 이탈했다면 다시 로그인해 설정 상태를 확인하세요.

## 세션과 자동화 API

MFA·Passkey 관리는 브라우저 세션 전용입니다. Bearer API 토큰으로 키 등록, 복구 코드 조회/발급, 재인증 또는 웹 세션 발급을 우회할 수 없습니다.

TOTP 변경·복구 코드 재발급·Passkey 등록/삭제는 기존 웹 세션과 인증 대기 상태를 폐기하고 현재 브라우저에만 새 세션·CSRF 토큰을 발급합니다. 보안 변경과 세션 발급은 함께 성공하거나 함께 롤백됩니다. 자동화 API 토큰은 유지합니다. 비밀번호·권한·활성 상태 변경과 아래 비상 복구는 현재 세션과 API 토큰도 폐기합니다. API 토큰은 MFA의 대체 수단이 아니므로 별도로 최소 scope와 만료를 관리하세요.

## 백업과 키 보호

데이터 디렉터리의 `auth.key`는 TOTP를 AES-256-GCM으로 암호화하는 32바이트 키입니다. Linux에서 새 데이터 디렉터리는 0700, 새 키 파일은 0600으로 생성합니다. Windows 개발 환경에서는 해당 폴더의 NTFS ACL을 사용자와 관리자에게만 허용하세요.

서버를 정상 중지하고 **데이터 디렉터리 전체, 특히 core.db와 auth.key를 함께** 백업하세요. SQLite WAL 파일이 남은 경우도 전체 백업에 포함합니다. DB만 복구하거나 다른 설치의 키를 가져오면 TOTP를 복호화할 수 없습니다. 키 누락/손상 시 자동으로 새 키를 만들거나 MFA를 해제하지 않습니다.

암호화는 DB 파일만 유출된 경우의 보호입니다. DB와 키가 함께 있는 호스트 전체가 탈취된 경우까지 보호하지 않습니다. 백업도 암호화하고 접근 권한을 제한하세요. HTTP로 접속하면 QR·시크릿과 비밀번호가 전송 중 노출될 수 있으므로 TOTP 설정에도 운영 HTTPS를 사용하세요.

이번 버전은 DB schema v3로 자동 마이그레이션합니다. 구버전 실행파일은 v3를 열지 못합니다. 롤백은 서버를 중지하고 **이전 실행파일과 업데이트 전 전체 데이터 백업**을 함께 복원해야 합니다.

## 모든 인증 수단을 잃었을 때

가능하면 auth.key 백업 복원 또는 복구 코드를 먼저 사용합니다. 서버 파일 접근 권한을 가진 운영자만 아래 오프라인 명령을 사용할 수 있습니다. 온라인 우회 API는 없습니다.

Docker Compose 예시입니다. 먼저 백업하고 중지한 뒤 계정명을 두 번 동일하게 지정합니다.

```sh
docker compose stop app
docker compose run --rm --no-deps app admin reset-mfa --data-dir /data --username admin --confirm-username admin
docker compose up -d --no-build
```

Linux 네이티브 예시입니다.

```sh
sudo systemctl stop modudock
sudo -u modudock /usr/local/bin/modudock admin reset-mfa --data-dir /var/lib/modudock --username admin --confirm-username admin
sudo systemctl start modudock
```

서버가 데이터 디렉터리를 사용 중이면 명령은 실패합니다. 해당 계정의 TOTP·복구 코드·Passkey·세션·API 토큰·인증 대기 상태를 삭제하고 감사 기록을 남깁니다. 비밀번호·역할·활성 상태는 변경하지 않습니다. 키가 손상되어도 복호화하지 않고 초기화할 수 있습니다.

명령은 auth.key를 자동 삭제하거나 교체하지 않습니다. 손상된 키는 가능한 원본 백업으로 복원하세요. 원본이 없으면 영향을 받은 모든 계정을 오프라인 복구하고, 운영자가 전체 백업과 암호문 부재를 확인한 뒤 손상된 키를 별도 보관해야 새 TOTP 설정에서 키를 생성할 수 있습니다. 다른 계정의 MFA가 남아 있는 상태로 키를 임의 교체하지 마세요.

실제 Windows Hello·휴대전화 QR 스캔은 사용하는 기기에서 별도로 확인해야 합니다. 브라우저 가상 인증기 검증은 실기기 검증을 대체하지 않습니다.
