# Linux 네이티브 설치 및 GitHub 게시 계획

## 목적과 설계
GitHub Release의 UI 내장 Linux 실행파일을 받아 systemd 서비스까지 등록하는 scripts/install.sh를 제공한다. 기존 Go 실행파일·계정 생성 명령·서비스 템플릿을 재사용하고 사용자의 서버에서 빌드하지 않는다.

- 대상은 systemd를 실행 중인 Linux amd64/arm64이다. DSM·비systemd·32비트는 변경 없이 실패한다.
- 고정 저장소 colaiuta77/modudock의 latest 또는 MODUDOCK_VERSION 지정 태그에서 아카이브와 SHA256SUMS를 내려받는다. 검증이 끝나기 전 서비스를 중지하거나 실행파일을 바꾸지 않는다.
- 설치는 /usr/local/bin/modudock, 데이터 /var/lib/modudock, 서비스 modudock.service, 계정 modudock을 사용한다. 기본 loopback 7438과 기존 서비스 설정을 보존한다.
- 처음에는 /dev/tty에서 관리자 이름·숨김 비밀번호를 입력한다. 기본 비밀번호를 생성하지 않으며 비밀값을 인자·환경변수·로그에 남기지 않는다. 터미널이 없으면 변경 전에 중단한다.
- 업데이트는 기존 서비스 중지 후 데이터 전체와 실행파일·서비스 파일을 /var/backups/modudock 아래 고유 디렉터리에 보존한다. DB 마이그레이션 때문에 실패 시 실행파일만 자동 복구하지 않고 전체 복구 방법을 안내한다.
- 원격 main의 README·AGPL 라이선스와 이력을 확인했다. README는 실제 Go 안내로 갱신하고 라이선스와 다른 브랜치는 보존한다. force push·기존 태그 변경은 하지 않는다. 사용자가 추가 승인한 v0.1.0 태그와 첫 릴리스는 게시한다.

## 작업과 검증
1. Bash 함수/명령 경계를 이용해 임시 폴더에서 다운로드 무결성, 아키텍처, 설정 보존, 전체 백업, 서비스 시작 실패를 재현하는 테스트를 먼저 작성한다.
2. scripts/install.sh를 구현하고 기존 릴리스 워크플로의 아카이브/체크섬 규약에 맞춘다. 설치 테스트를 CI에 추가한다.
3. README·설치 안내를 실제 저장소 주소와 첫 릴리스 전 상태에 맞춰 갱신한다.
4. Bash 문법·설치 테스트, Go tests/vet, frontend tests/build, 독립 보안 리뷰를 수행한다.
5. 관련 소스만 커밋하고 기존 원격 main을 조상으로 보존한 정상 push로 게시한다. 검증된 커밋에 v0.1.0 태그를 발행하고 Actions 완료와 실제 릴리스 아카이브·체크섬 다운로드를 확인한다.

## 범위 밖
자동 방화벽 개방, HTTPS 프록시 설치, DSM 서비스 등록, 무인 비밀번호 환경변수, 제거/데이터 삭제는 추가하지 않는다.
